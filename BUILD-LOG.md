## SEC.1 · Auth foundation (SPEC-SECURITY §1) — 2026-07-08

**Context:** first step of the security track from `BUILD-EXECUTION-PLAN.md` (the 8-agent whole-platform synthesis). Security is the true critical path: there was **no real auth** — `actor` was whatever the request body claimed and no route was session-scoped. SEC.1 closes the front door; SEC.2 (2FA), SEC.3 (RBAC + actor-from-principal), SEC.4 (tenant isolation) build on it.

**Built:** email+password auth with server-side sessions. (1) **Migration 0005** — `users.{email unique, password_hash}` + a `sessions` table (token_hash, 12h idle / 7d absolute expiry, revoked_at). (2) **`server/src/auth.ts`** — scrypt hash/verify (per-user salt, `timingSafeEqual`), `createSession` (opaque 32-byte token, only its sha256 stored), `validateSession` (checks revoke + both expiries, slides the idle window), `revokeSession`, httpOnly+SameSite=Lax cookie, and a `requireAuth` Hono middleware that 401s without a valid session and sets `c.get('principal')`. (3) **API** — `POST /api/auth/login` + `/logout` registered public, then `app.use('/api/*', requireAuth(db))` gates every route below; `/api/health` + `/hooks/*` stay public (webhooks get HMAC at SEC.6). (4) **Seed** — the 4 agency users get emails + a dev password (`demo2080`, e.g. `wally@2080.dental`). (5) **App** — `LoginPage` + `AuthGate` (checks `/api/auth/me`; shows login when anon, the app when authed) mounted **only in `main.tsx`** so component/shell tests that render pages directly are unaffected; a Sign-out control in the topbar.

**Evidence:** server **62/62** — 3 new in `auth.test.ts` (protected routes 401 without a cookie · bad + unknown credentials refused · login issues an httpOnly SameSite=Lax `sid` cookie that authorizes `/api/*` and resolves the owner principal on `/api/auth/me` · logout revokes so the same cookie then 401s), and the 4 existing HTTP suites (today/audit/skills/notify) now authenticate through a shared `test/helpers.ts` `authed()` login helper. App **17/17** — 3 new `AuthGate` tests (anon→login form, authed→app, sign-in reveals the dashboard). Both typecheck; app lint clean; `vite build` green. (Windows note: repeated runs orphan `postgres.exe` on the fixed test ports and stall `afterAll`; `taskkill //F //IM postgres.exe` then a fresh run is 8/8 green — a pre-existing embedded-PG flake, not a logic failure.)

**Files:** `server/migrations/0005_auth.sql`, `server/src/auth.ts`, `server/test/{auth.test.ts, helpers.ts}` (new) · `server/src/{api.ts, db/seed.ts}` + `server/test/{today,audit,skills,notify}.test.ts` (edits) · `app/src/app/{LoginPage,AuthGate,AuthGate.test}.tsx` (new) · `app/src/{main.tsx, app/AppShell.tsx}` (edits).

**Decisions:** (1) **Cookie-session, not JWT** — SPEC §1 requires revoke-all on role change/offboard and refresh rotation; server-side sessions make revocation real (a JWT can't be un-issued). (2) SEC.1 gates *access* only — routes still read `actor` from the body; wiring `actor = c.get('principal')` server-side is **SEC.3**, and per-row tenant scoping is **SEC.4**. Deliberately not done here to keep the step small. (3) Gate lives in `main.tsx`, not inside `AppRoutes`, so the existing component/shell tests need no auth mocking. (4) Dev password is seed-only and clearly marked; real credential handling + login-notify + lockout are SEC.6. (5) 2FA (SEC.2) and portal magic-link (SEC.5) are separate steps per the spec.

Matcher implements SPEC-SPINE §3 exactly, deterministic first: ① exact source-ref maps (phone DID / Ads / BrightLocal / GBP / portal session / AC project) → 1.0 · ② contact email exact ∪ learned email mappings → 0.98, ties always queue · ③ thread continuity → 0.97 · ④ domain (entity_maps ∪ contact-email domains) → 0.90, shared domain never autos · ⑤ fuzzy signature-name/phone → ≤0.7, always queues · nothing → prospect. `ingestEvent` routes inbound events: auto-attach to `timeline_events` (learning the thread mapping so stripped replies match on continuity), hold in `match_queue`, or park as prospect for the sales flow. `resolveMatch` turns a human's queue choice into an `entity_maps` row — the matcher learns — then attaches the held event and audits. New `match_queue` table because `timeline_events.client_id` is deliberately NOT NULL: unmatched events never touch the timeline.

**Evidence:** golden set `server/test/golden/matcher.golden.json` — 30 inbound events across all five tiers routed **30/30** (DoD floor ≥29/30 = 95%) · every queue decision confidence <0.8, every auto ≥0.8 · shared-domain case queues with both candidates, never guesses · queue resolution learns: bentrowse@gmail.com queued (fuzzy 0.6) → resolved to Trowse → same sender autos at 0.98 next time · resolved items can't resolve twice · prospects held in queue state `prospect`, off the timeline. Full server suite 30/30, app 8/8, typechecks clean.

**Files:** `server/src/matcher.ts`, `server/migrations/0002_match_queue.sql`, `server/test/{matcher.test.ts, golden/matcher.golden.json}` (new) · `seed.ts` (contact phone numbers added for the fuzzy tier).

**Decisions:** (1) `match_queue` is a new table the spec's "human queue" implies but §2 doesn't name — refs + held event + candidates, states open/resolved/prospect/dismissed. (2) Shared domains are detected via contact-email domains (entity_maps has a uniqueness constraint per kind+key, so a shared domain can't be two mapping rows — the management-group scenario lives in contacts). (3) On resolve, the most specific ref is learned (email > phone), plus the thread. (4) Match-queue UI lands with Inbox (1.5), which is this queue's production surface.
